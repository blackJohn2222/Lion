# Odyssey 面试学习冲刺设计

> 日期：2026-08-24
> 状态：设计已通过对话确认，等待文档审阅
> 目标：在三天内通过对话和 Unity 实操，建立对 Odyssey 项目核心功能的可解释、可追问、可复现的理解。

## 1. 背景与约束

- 面试岗位是 Unity 客户端开发。
- 面试在三天后，每天可投入四小时以上。
- 面试形式以口头介绍和项目追问为主。
- 简历已经投递，项目介绍包含有限状态机、角色物理与关卡交互、Shader 渲染三条主线。
- 目前看过 Odyssey 角色代码，但对完整运行流程、Unity 配置和实现细节缺乏稳定理解。
- 学习期间可以打开 Odyssey Unity 项目，查看 Inspector、Prefab、场景并运行验证。
- 初期不实现 Lion 或 Odyssey 的代码；必要代码只作为对话中的解释片段。
- Lion 当前 Day 3 代码只作为由浅入深的练习材料，不替代 Odyssey 的实际代码和配置证据。

## 2. 学习目标

三天结束时，用户能够围绕 Odyssey 完成可信的项目介绍，并回答从功能细节延伸出的 Unity、C#、设计模式、架构和性能问题。

每个重点功能都必须能够回答以下问题：

1. 功能解决了什么游戏问题？
2. 场景、Prefab、GameObject 和 Inspector 如何配置？
3. 使用了哪些 Unity 内置系统、组件和第三方插件？
4. 从输入、生命周期或事件到最终结果的运行时调用链是什么？
5. 各脚本、组件和数据资产分别负责什么？
6. 使用了什么设计模式或架构原则？为什么这样设计？
7. 如果换一种实现方式，有什么收益和代价？
8. 如何增加一个新状态、新交互物、新敌人行为或新渲染效果？

## 3. 学习范围

### 3.1 P0：简历必须守住

- Player 和 Enemy 的有限状态机。
- 代码状态机和 Animator 状态机的协作。
- Input System 的动作、绑定和输入门面。
- CharacterController、速度、重力、地面检测和移动。
- Collider、Trigger、Layer、Tag 和物理检测。
- 沼泽、泳池、木箱、滑轨、传送门和检查点的交互链路。
- 基于深度纹理的世界空间扫描 Shader。

### 3.2 P1：架构与设计模式

- `Entity<T>`、CRTP 和泛型约束。
- 模板方法、状态模式和策略容器。
- Facade 输入门面。
- ScriptableObject 数据驱动和多套数值配置。
- UnityEvent 与观察者式事件通知。
- 继承和组件组合的取舍。
- Player 与 Enemy 的通用实体复用。
- Unity 生命周期、模块边界和程序集依赖。
- 物理检测时机、更新循环和常见性能风险。

### 3.3 P2：扩展和加分项

- Cinemachine 第三人称相机。
- `Time.timeScale` 和暂停系统。
- `EntityStateManagerListener` 表现层挂钩。
- 接触接口、移动平台和区域效果器。
- 动画、粒子、音频和脚步表现层。
- 物理查询、GC、材质实例和 Shader 参数更新的性能问题。
- 单机角色架构向网络同步角色的演进方向。

非主线的功能只在能够帮助解释架构或应对追问时展开，不按 Odyssey 的全部脚本逐文件通读。

## 4. 每个学习单元的固定结构

每个单元围绕一个可验证的问题，例如“玩家按下移动键后如何进入 Walk 状态”。固定顺序如下：

1. 说明功能目标和玩家可见结果。
2. 在 Odyssey 中定位场景、Prefab、GameObject 和组件。
3. 检查 Inspector、Input Actions、Animator、材质、Layer、Tag 或其他资产配置。
4. 从 Unity 生命周期、输入入口、碰撞回调或事件入口追踪代码。
5. 画出对象、组件、脚本、状态和数据之间的调用链。
6. 解释设计模式、职责边界、依赖方向和替代方案。
7. 用户先预测调用链，再用自己的话复述。
8. 以面试官身份追问 Unity、C#、架构、性能和扩展性。
9. 必要时只贴当前问题相关的代码片段并逐段解释。
10. 形成 30 秒回答和 2 分钟回答。

每个单元的学习记录采用以下结构：

```text
功能目标
Unity 对象与配置
关键脚本和入口
运行时调用链
数据与事件流
设计模式与职责边界
替代方案与取舍
常见错误与调试方式
30 秒面试回答
2 分钟面试回答
面试官追问
```

## 5. 三天安排

### 5.1 第一天：角色运行主链路

目标：能从场景启动讲到角色每帧移动，并说明状态机和动画状态机如何协作。

学习内容：

- `TestLevelScene`、Player Prefab、Camera 和 Level 对象的关系。
- `Awake`、`OnEnable`、`Start`、`Update` 和 `LateUpdate` 的实际调用位置。
- Player 上的 CharacterController、状态管理器、输入管理器、数值管理器和事件对象。
- `EntityBase → Entity<T> → Player` 的继承关系。
- `EntityState<T>`、`EntityStateManager<T>` 和 Player 状态注册。
- Idle、Walk、Fall 的进入、退出、逐帧执行和切换条件。
- Input System 到状态决策、Player 能力方法、速度和 CharacterController 的链路。
- 状态机参数如何进入 Animator Controller，动画如何反馈表现层。
- 状态模式、模板方法、CRTP、Facade、组件组合和数据驱动。

当天验收：

- 不看代码讲出角色主调用链。
- 指出 Player Prefab 上的核心组件及其作用。
- 解释为什么代码状态机和 Animator 状态机不是同一个状态机。
- 完成一轮项目介绍和状态机追问。

### 5.2 第二天：运动系统与关卡交互

目标：能解释角色运动的来源、碰撞交互的接入方式以及 Enemy 状态复用。

学习内容：

- Input Action、Action Map、Control、Binding 和输入资产配置。
- CharacterController 与 Rigidbody 的工作方式、适用场景和取舍。
- 加速度、减速度、速度上限、重力、地面检测、斜坡和滑轨。
- Collider、Trigger、Layer、Tag 和物理查询 API 的职责区别。
- 沼泽、泳池、木箱、滑轨、传送门和检查点的对象配置及调用链。
- Enemy 定点巡逻、跟随和实体/状态架构复用。
- 观察者式事件、策略、继承与组合、依赖倒置和扩展新状态。
- Update、FixedUpdate、触发器时机、物理层过滤和常见空引用问题。

当天验收：

- 从任意一个交互物体反向讲出完整交互链路。
- 解释为何某些功能使用 Trigger，而不是直接依赖状态机。
- 设计一个新 Enemy 状态，并指出需要新增或修改的位置。
- 完成一轮 Unity 系统和架构追问。

### 5.3 第三天：Shader、工程化总结与模拟面试

目标：守住简历中的 Shader 亮点，并把项目功能、Unity 技术和架构取舍串成稳定回答。

学习内容：

- URP 渲染路径和深度纹理的作用。
- 世界空间位置如何参与扫描效果计算。
- 箱子落地事件如何启动扫描效果。
- 脚本如何更新扫描中心、半径、宽度、强度和消失过程。
- 深度比较、距离计算和边缘衰减的含义。
- Shader、Material、材质实例、参数更新和性能风险。
- Input System、Cinemachine、URP、Animator、CharacterController、Physics、UnityEvent 和 ScriptableObject 的项目用途。
- 角色层、关卡层、表现层和渲染层的边界。
- 如何增加新状态、新交互、新特效，以及如何避免模块耦合。
- 两轮模拟面试：项目介绍与简历追问；Unity、C#、模式、架构和性能追问。

当天验收：

- 能用 30 秒说明扫描效果的触发、数据传递和视觉结果。
- 能用 2 分钟说明一条完整角色或交互链路。
- 能比较至少两组关键替代方案。
- 完成两轮模拟面试并整理剩余薄弱点。

## 6. 面试回答策略

回答采用三档深度：

- 30 秒版：功能、关键技术和结果。
- 2 分钟版：Unity 配置、调用链、职责和设计原因。
- 深挖版：替代方案、扩展方式、性能风险和调试方法。

用户曾经主要通过复制代码接触 Odyssey，因此回答以项目事实和当前理解为基础，不编造独立设计经历。遇到个人贡献边界问题时，优先准确说明“项目使用了什么、代码如何工作、自己现在能够解释和复现什么”。

## 7. 验证与事实分层

每个结论标记其证据来源：

- 代码确认：来自脚本、方法和字段。
- 编辑器确认：来自 Inspector、Prefab、场景或资产配置。
- 运行确认：来自 Play Mode 的实际行为。
- Unity 机制推断：基于引擎规则但尚未在项目中验证。

静态代码不能确定的行为必须通过 Unity 编辑器或运行结果验证。验证优先检查场景引用、组件存在、输入资产、Animator 参数、材质参数、Layer/Tag 和事件绑定。

## 8. 错误处理与学习分支

- Unity 编译或运行错误时，先保留完整原文，分析涉及的脚本、组件、资产和包依赖，等用户审核后再修改代码。
- 如果代码和运行表现不一致，按场景、Prefab、组件、生命周期、事件和渲染参数逐层排查。
- 用户答不出时，按“关键词 → 上一个调用节点 → 关键代码片段 → 完整解释”的顺序增加提示。
- 用户能够稳定回答后，立即进入设计题或扩展题，避免继续重复基础内容。
- 如果发现简历表述与项目事实之间有风险，先建立可信回答边界，不用额外概念掩盖理解缺口。

## 9. 设计取舍

本计划选择“简历三主线逆向复盘”为主，融合项目地图和 Unity 技术实验，而不是平均扫描全部目录：

- 相比逐目录通读，主线复盘能建立完整运行故事。
- 相比纯面试题训练，先建立事实链能减少碎片化背诵。
- 相比纯 Unity 技术实验，把系统放回 Odyssey 场景能解释配置为什么存在。
- 相比立即实现 Lion，先理解 Odyssey 能避免把复制行为误认为掌握。

## 10. 最终完成标准

计划完成不以读完多少文件或写出多少代码为标准，而以以下能力为标准：

- 能完成可信的 Odyssey 项目介绍。
- 能完整讲清有限状态机、角色运动/交互和 Shader 三条主线。
- 能指出关键 Unity 系统、组件、插件、资产和 Inspector 配置。
- 能从入口讲到结果，并区分状态、事件、组件和数据的职责。
- 能解释主要设计模式、架构原则、替代方案和取舍。
- 能回答新状态、新交互、新敌人行为和新特效的设计题。
- 能说明已确认事实、运行验证结果和暂时的合理推断之间的区别。
- 完成至少两轮模拟面试，并保留未掌握问题清单。
